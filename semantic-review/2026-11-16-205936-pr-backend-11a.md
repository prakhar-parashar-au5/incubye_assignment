# Temporary-password recovery for Admin-managed HR accounts

This correction marks replayed HR-user creation as requiring credential recovery and adds an Admin-only preview-and-confirm regeneration operation. Regeneration uses the existing ordered-lock, expected-version, preview-token, idempotency, session-revocation, version, and audit transaction path; plaintext exists only long enough to return the first successful response. The original Task 11 blocker is resolved for another HR user, but self-regeneration can recreate the same lost-response lockout, and sign-in is not serialized with password replacement.

**Watch for:** **confirmed** sole-Admin lockout after a lost self-regeneration response; **likely** an old-password sign-in race that creates an unrevoked session after regeneration.

**Verdict**: NEEDS_CHANGES

## High-level view

Create replay now returns `temporaryPassword: null` with `credentialRecoveryRequired: true`. Same-key regeneration replay is checked before stale-version rejection and returns the original user/audit outcome without changing the hash or version again.

Regeneration permits self-targeting and revokes the session authorizing the command. If that response is lost and no other active Admin exists, the actor has neither the new password nor a valid session for another regeneration.

Sign-in verifies the password before inserting its session, outside the regeneration transaction. A sign-in that verifies the old hash before regeneration but inserts after the revocation update can leave a valid session created from the invalidated password.

## Self-regeneration can strand the sole Admin

**Confirmed:** the route accepts any positive `hrUserId`, and the service/domain path has no self-target or last-active-Admin guard (`express-backend/src/http/hr-access-routes.ts:188-204`, `express-backend/src/access/hr-access-service.ts:622-661`, `express-backend/src/access/hr-users.ts:661-674`). The shared transaction revokes every active target session (`express-backend/src/access/hr-users.ts:471-479`), including the session that authorized a self-regeneration.

If the response is lost, request authentication rejects that revoked session before replay can reach the idempotency check. A fresh preview also requires an active Admin session. A sole Admin is therefore locked out, recreating the failure Task 11a exists to remove. The new tests cover only other Scoped targets (`express-backend/test/db/hr-access.test.ts:941-1174`). Reject self-regeneration, or reject it when no other active Admin can recover the account, and test the chosen rule as a lost-response journey.

## Old-password sign-in can survive the regeneration boundary

**Likely:** sign-in reads and verifies `password_hash`, then inserts the session in a separate statement with no target-row lock or post-wait password/version recheck (`express-backend/src/access/sessions.ts:101-123`). Regeneration updates the hash and revokes only sessions visible before its revocation statement (`express-backend/src/access/hr-users.ts:461-486`, `express-backend/src/access/hr-users.ts:661-674`).

A request can verify the old hash, pause, let regeneration update the hash and revoke sessions, then insert a new unrevoked session. A foreign-key lock may delay the insert, but it does not rerun password verification after the wait. Serialize sign-in with password replacement, or revalidate the password/version in the same transaction immediately before session creation, and add a deterministic old-password sign-in versus regeneration test.
