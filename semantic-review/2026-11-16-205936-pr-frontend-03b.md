# Trustworthy salary approval context and completion states

Frontend Task 03b closes both blockers from the first salary UI review. Admin request detail now shows the backend-selected base salary, bonus, annual cash compensation, native currency, compensation version, effective date, and state before decision controls. Salary action outcomes now come from persisted records; URL values can select an existing history row for emphasis but cannot claim that the current browser performed an apply, submit, approval, or cancellation. The generated-contract check, lint, route type generation, 157 unit/component tests, and Next.js 16.4.6 production build pass.

**Watch for:** No blocking concerns remain. The browser suite was not independently rerun in this review; the builder reports 66 passing and 4 pre-existing project-specific skips, including 18 salary journeys across desktop and mobile.

**Verdict**: APPROVED

## High-level view

The request detail uses the employee response it already fetched for stale-version detection to render the full selected compensation record. Decision controls render only when that record is available. The requested target’s exact before/after values, reason, note, effective date, and requested-against version remain separate and visible.

Pending, approved, cancelled, and stale messaging comes from the persisted request. Approval and cancellation call `router.refresh()`; the API client uses `cache: 'no-store'`, so the refreshed request and employee history are read from Express rather than a server fetch cache.

Direct apply still carries `applied=<version>` as a presentation hint. The employee page validates the version, finds it in backend-provided history, and displays neutral copy describing the highlighted record. Real-browser tests cover crafted and contradictory `submitted`, `decided`, and `applied` values.
