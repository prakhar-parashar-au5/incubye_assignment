# Final dashboard commitment and HR access race fixes

Task 11b closes the remaining backend findings in commitment accounting, password regeneration, sign-in serialization, dashboard failure coverage, and measurement evidence. Soon-to-join commitments now include approved later adjustments without double-counting the selected same-day version. Password replacement and sign-in serialize on the HR-user row, and both regeneration endpoints reject self-targeting before password generation or writes. The focused implementation and evidence match the task; this review did not rerun database tests because no isolated test URL was provided outside prohibited environment files.

Watch for: **confirmed, non-blocking** — the saved measurements still reproduce an approximately 11-second first Admin summary immediately after a bulk load. Task 11b documents this as an open operational decision rather than claiming it is fixed.

**Verdict**: APPROVED

## High-level view

The dashboard keeps selected soon-to-join cash in the initial-compensation aggregate and expands future impact to working and soon-to-join employees. Excluding the selected version makes a same-day higher version contribute through initial cash only; later-dated adjustments contribute their signed difference once (`express-backend/src/dashboard/dashboard-service.ts:222-252`, `express-backend/test/db/dashboard-commitment.test.ts:7-27`).

Known-user sign-in takes a shared HR-user lock and inserts its session in the same transaction. Regeneration takes a conflicting update lock before replacing the hash and revoking sessions, so either it revokes the newly inserted session or sign-in reads the replacement hash and rejects the old password (`express-backend/src/access/sessions.ts:99-153`, `express-backend/src/access/hr-users.ts:487-527`).

Self-regeneration is rejected for preview and confirmation and again in the domain operation. The public 409 code and message are present in the runtime contract and both OpenAPI operations (`express-backend/src/access/hr-access-service.ts:608-645`, `express-backend/src/access/hr-users.ts:657-676`, `express-backend/src/http/contract.ts:68-87,160-179`, `express-backend/src/http/openapi.ts:515-549`).

Dashboard tests cover recognized connectivity and lock-timeout failures across all four routes, assert the fixed 503 response, and prevent SQL, connection details, stack text, and query values from reaching responses or logs. Unexpected errors remain on the 500 path (`express-backend/test/http-dashboard-errors.test.ts:10-72`).

The replacement evidence records two fifteen-run measurements and a controlled statistics experiment. It preserves the slow first summary and supports stale optimizer statistics as the cause without overstating certainty (`builder_docs/responses/11b-dashboard-measurements.txt:1-5,165,712-720`, `builder_docs/responses/11b-dashboard-statistics-experiment.txt:1-18`).

## Soon-to-join commitment and same-day versions

The selected-compensation query chooses the earliest future date for a joiner and the highest version on that date. The impact query includes non-import future records for working and soon-to-join employees but excludes `f.version = sc.version`; a selected same-day version is represented by initial cash, while a later-dated version contributes its difference.

The real-MySQL fixture covers increases, decreases, INR and USD, Admin and scoped access, filters, a working employee, a left employee, and a same-day higher version. It also makes the count behavior explicit: the same-day adjustment appears in the upcoming list but not the impact count because its value is already selected (`express-backend/test/db/dashboard-commitment.test.ts:89-181`).

## Password replacement ordering

Sign-in uses `READ COMMITTED` and holds `FOR SHARE` from the identified-user read through session insertion and commit. The unknown-email path rolls back before its one dummy Argon2 verification, preserving the one-verification behavior without retaining an empty-key lookup lock.

The concurrency tests force both orders. Sign-in-first pauses after verification while the shared lock is held and observes regeneration at its update-lock statement. Regeneration-first holds regeneration during session revocation after it has locked the user, then observes old-password sign-in at its shared-lock statement. Final assertions cover session revocation and new-password usability (`express-backend/test/db/hr-access.test.ts:1174-1260`).

## Self-regeneration contract

Preview rejects actor equals target immediately after path-ID parsing. Confirmation rejects before token validation, password generation, hashing, reads, or writes. Tests compare hash, sessions, scopes, version, and audit state before and after rejection for an Admin with another Admin and for the sole active Admin (`express-backend/test/db/hr-access.test.ts:1153-1172,1328-1341`).

## Dashboard failure boundary

The route tests inject mysql2-shaped failures through the real Express app. Six recognized codes map to `503 SERVICE_UNAVAILABLE`; a `TypeError`, parse error, and access-denied error remain `500 INTERNAL_ERROR`. Response and log assertions include embedded SQL and connection material (`express-backend/src/http/dashboard-routes.ts:24-43`, `express-backend/test/http-dashboard-errors.test.ts:35-72`).

## Measurement evidence and remaining risk

The Task 10 response now distinguishes its original three-run plan file from recovered fifteen-run output. Fresh evidence declares 15 runs for two Admin and scoped runs. A separately rebuilt dataset measures an Admin summary at about 11.4 seconds immediately after load and 50 ms after `ANALYZE TABLE` (`builder_docs/responses/10-dashboard-analytics-api.md:141-166`, `builder_docs/responses/11b-dashboard-statistics-experiment.txt:1-18`).

The experiment supports stale statistics but cannot inspect optimizer-stat tables because the test user lacks access. The response keeps that limitation and leaves `ANALYZE TABLE` as an open decision (`builder_docs/responses/11b-backend-final-review-fixes.md:205-250`).
