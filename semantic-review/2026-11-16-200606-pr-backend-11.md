# Admin HR access-management API

This change adds Admin-only HR-user listing, exact access previews, user creation, profile and scope changes, promotion, activation state changes, session revocation, and immutable audit reads. It reuses the existing access policy and audit table, serializes writes with ordered HR-user locks, binds confirmations to signed five-minute previews, and records idempotency fingerprints with the audit event. Backend lint, TypeScript, all 381 fast tests, and the production build pass, but create replay does not return the original result and can leave a successfully created account permanently unusable after a lost response.

**Watch for:** **confirmed** unrecoverable temporary password when the original create response is lost.

**Verdict**: NEEDS_CHANGES

## High-level view

All routes authenticate first and reject non-Admin users before parsing mutation bodies. Writes recheck the actor under row locks; target updates compare `hr_users.version`; promotion and deactivation revoke sessions in the same transaction as the version and audit event. The preview token and operation fingerprint cover separate concerns: exact confirmation and retry identity.

Creation generates and hashes a random temporary password before the transaction. The first response returns it, while an idempotent replay returns the same user and audit event with `temporaryPassword: null`. If the original HTTP response is lost, the Admin has no way to retrieve the password, the user cannot sign in, the email is occupied, and password reset is outside this version.

## Create replay loses the only usable credential

**Confirmed:** the specification requires a retry action for uncertain mutations using the same idempotency key and says the same key with the same command returns the original result (`docs_human/12-hr-access-management.md:374, 433`). The service intentionally returns `temporaryPassword: null` on replay (`express-backend/src/access/hr-access-service.ts:545-546`), and the contract says the original value cannot be shown again (`express-backend/src/http/contract.ts:939, 1131-1138`). The integration test locks in that behavior (`express-backend/test/db/hr-access.test.ts:361-384`).

A network timeout after commit therefore creates an active user whose only credential was never received. The Admin cannot recreate the same email and this release deliberately has no password-reset operation. Resolve the product conflict before exposing creation in the frontend. Options include deriving the temporary password deterministically from a server secret and the idempotency operation, retaining an encrypted credential for a tightly bounded replay window, or adding an Admin credential-regeneration operation. Whichever policy is chosen, the same-key retry test must cover a lost first response and prove the account remains usable without storing or logging plaintext.
