# Permission-aware compensation dashboard analytics

Task 10 adds four authenticated read endpoints for summary figures, native-currency breakdowns, recent compensation changes, and employees without a recent recorded adjustment. Scope filtering and aggregation run in MySQL; DECIMAL values remain strings and BigInt helpers perform exact division and signed totals. Recent changes use `created_at`, and empty HR scope suppresses all figures and rows. The upcoming-commitment calculation misses an allowed approved future adjustment for a soon-to-join employee.

Watch for: **confirmed** — a soon-to-join employee’s approved non-import future adjustment appears in the upcoming list but does not affect its commitment total; **confirmed** — no fixture covers this case; **confirmed** — the saved timing artifact contains three runs although the response claims fifteen-run results.

**Verdict**: NEEDS_CHANGES

## High-level view

Every dashboard query applies country-and-department scope in SQL before aggregation, ranking, or pagination. Admin, scoped, empty-scope, and filter-widening fixtures cover the principal data paths.

Current spending and breakdown money remain separated by native currency. SQL selects median rows, then exact BigInt division applies half-up rounding to averages and medians.

Recent changes use creation time, exclude `INITIAL_IMPORT`, include recently recorded future-effective changes, and use bounded pagination. The no-adjustment path also excludes imports and limits its population to currently working employees.

Upcoming commitment combines selected compensation for soon-to-join employees with future-record deltas only for currently working employees. This omits an approved later record for a soon-to-join employee even though the salary workflow allows one and the dashboard lists it as upcoming.

## Soon-to-join adjustments are absent from commitment totals

**Confirmed.** The joiner aggregate uses only `sc`, the selected compensation row for each `SOON_TO_JOIN` employee (`express-backend/src/dashboard/dashboard-service.ts:227-232`). The future-impact aggregate explicitly restricts `e.employment_status = 'CURRENTLY_WORKING'` (`express-backend/src/dashboard/dashboard-service.ts:234-242`). The upcoming list includes non-import future records for both working and soon-to-join employees (`express-backend/src/dashboard/dashboard-service.ts:244-261`).

The salary workflow permits an adjustment for a soon-to-join employee and one non-import future record (`express-backend/src/compensation/salary-adjustment-service.ts:280-296, 334-354`). If a joiner has an imported INR 1,000,000 package effective on the joining date and an approved INR 1,100,000 adjustment effective later, the summary still reports INR 1,000,000. The adjustment appears in `upcomingChanges.items`, so the list and total disagree.

The commitment calculation should include the signed joiner adjustment or select the final approved future amount, depending on the intended product definition. Current-working behavior can remain unchanged.

## Native money and deterministic median

Current spending groups by `sc.currency`, and breakdown ranking partitions by group and currency (`express-backend/src/dashboard/dashboard-service.ts:220-225, 382-405`). Median selection uses one middle row for odd groups or two for even groups; `averageMoney` divides integer minor units and rounds half-up (`express-backend/src/money/decimal.ts:30-37`). Fixtures cover odd, even, repeating-decimal, half-cent, and separated INR/USD cases (`express-backend/test/db/dashboard.test.ts:293-327`). A missing INR/USD rate leaves native values available (`express-backend/src/dashboard/dashboard-service.ts:176-189, 269-277`).

## Scope and incompatible filters

Parameterized scope and metric-specific filters enter each query before aggregation or pagination (`express-backend/src/dashboard/dashboard-service.ts:132-141`). Out-of-scope Finance/US fixture rows test every summary metric, breakdowns, recent rows, no-adjustment rows, empty scope, and filter-widening attempts (`express-backend/test/db/dashboard.test.ts:212-253`).

Non-working `employmentStatus` filters are intentionally not applied to working-only spending and non-status breakdowns; these sections return a `notApplied` reason and retain the working population (`express-backend/src/dashboard/dashboard-service.ts:144-148, 368-375`; `express-backend/test/db/dashboard.test.ts:256-265, 344-348`). This follows the specification’s explicit incompatible-filter behavior.

## Recorded-time and no-adjustment boundaries

Recent changes filter `c.created_at` within 7, 30, or 90 days and exclude `INITIAL_IMPORT`; effective date only marks a result as future effective (`express-backend/src/dashboard/dashboard-service.ts:461-510`). Tests include a recently recorded future change and exclude an older record with a recent effective date (`express-backend/test/db/dashboard.test.ts:351-381`). Ordering is stable on `created_at DESC, id DESC`, and list/count predicates match.

No-adjustment results include currently working employees with no non-import record created inside the selected month window (`express-backend/src/dashboard/dashboard-service.ts:351-360, 516-548`). The response uses the approved import-safe wording, and fixtures verify count/list agreement and pagination (`express-backend/test/db/dashboard.test.ts:385-404`).
